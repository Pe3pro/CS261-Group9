U1:T4 : Requirement กำหนดรายละเอียด User Story
-
User story U1: นักศึกษาและเจ้าหน้าที่เข้าสู่ระบบด้วย Username และ Password ของสำนักทะเบียน (บัญชี มธ.) เพื่อเข้าใช้งานแอปพลิเคชัน

User story
-
- **As a** นักศึกษา มธ. และเจ้าหน้าที่ / อาจารย์ที่มี Username และ Password ของสำนักทะเบียน
- **I want to** เข้าสู่ระบบด้วยบัญชี มธ. ที่มีอยู่แล้ว
- **So that** เข้าใช้งานแอปพลิเคชันได้โดยไม่ต้องสมัครบัญชีใหม่ และเห็นเฉพาะเมนูของบทบาทตัวเอง

Pain point ของระบบเดิม
-
| ผู้ได้รับผลกระทบ | ปัญหา |
|---|---|
| นักศึกษา | ถ้าต้องสมัครบัญชีใหม่สำหรับระบบสหกิจ ต้องจำรหัสผ่านเพิ่มอีกชุด และลืมง่าย |
| นักศึกษา | ข้อมูลพื้นฐาน (รหัส ชื่อ คณะ สาขา) ต้องกรอกเองซ้ำทุกครั้ง และพิมพ์ผิดได้ |
| เจ้าหน้าที่ / อาจารย์ | ไม่แน่ใจว่าผู้ยื่นคำร้องเป็นนักศึกษาจริง · ต้องแยกเองว่าใครควรเห็นหน้าไหน |
| ทีมพัฒนา | ถ้าเก็บรหัสผ่านเองต้องรับผิดชอบความปลอดภัยของรหัสผ่านทั้งหมด |

Stakeholder
-
| Stakeholder | ความต้องการต่อ U1 | หน้าเว็บ |
|---|---|---|
| นักศึกษา (STUDENT) | login ด้วยบัญชี มธ. แล้วไปหน้าตรวจสอบคุณสมบัติ (U2) ต่อได้ทันที | `login.html` → `check.html` |
| เจ้าหน้าที่ฝ่ายสหกิจ (STAFF) | login แล้วเห็นเมนูตรวจใบสมัครและแบบฟอร์มคำร้อง (U5) | `login.html` → `staff-review.html` |
| อาจารย์ที่ปรึกษา (ADVISOR) | login แล้วเห็นเมนูพิจารณาใบสมัคร (U5) | `login.html` → `staff-review.html` |
| สำนักทะเบียน (TU REST API) | เป็นผู้ตรวจ Username / Password และให้ข้อมูลชื่อ คณะ สาขา ประเภทบัญชี | – |
| User Story อื่น (U2–U5) | ได้ `userId` และ `role` ของผู้ใช้ที่ login แล้ว ไปใช้ตรวจสิทธิ์ | – |

ขั้นตอนการทำงาน
-
1. ผู้ใช้เปิด `login.html` กรอก Username (รหัสนักศึกษา / รหัสบุคลากร) และ Password แล้วกดเข้าสู่ระบบ
2. หน้าเว็บตรวจว่ากรอกครบ ถ้าไม่ครบแจ้งเตือนโดยไม่ส่งไปที่ server
3. Backend ส่ง Username / Password ไปตรวจกับ TU REST API (ระบบไม่เก็บรหัสผ่านเอง)
4. ถ้าถูกต้อง: ผู้ใช้ใหม่ → บันทึกลงตาราง `users` (และ `students` ถ้าเป็นนักศึกษา) · ผู้ใช้เดิม → ใช้ role เดิม อัปเดตชื่อ / อีเมล
5. Backend ส่ง token, `userId` และ `role` กลับ หน้าเว็บเก็บใน `sessionStorage` แล้วพาไปหน้าหลักตาม role
6. ถ้าไม่ถูกต้อง หรือระบบ มธ. ขัดข้อง แสดงข้อความในกล่องสีแดงให้ลองใหม่
7. กดออกจากระบบ → ล้างข้อมูล login แล้วกลับหน้า login

Use case
-
| UC | ชื่อ | ผู้ใช้ | เงื่อนไขก่อน | ผลลัพธ์ |
|---|---|---|---|---|
| UC-01 | นักศึกษา login ครั้งแรก | นักศึกษา | มีบัญชี มธ. ยังไม่เคยใช้ระบบ | ระบบสร้างผู้ใช้ role `STUDENT` และข้อมูลนักศึกษา แล้วไป `check.html` |
| UC-02 | login ซ้ำ | ทุกคน | เคย login แล้ว | ใช้ข้อมูลเดิม ไม่สร้างแถวเพิ่ม ไปหน้าหลักตาม role |
| UC-03 | เจ้าหน้าที่ / อาจารย์ login | เจ้าหน้าที่, อาจารย์ | มี role `STAFF` / `ADVISOR` ในระบบ | ไป `staff-review.html` เห็นเฉพาะเมนูของบทบาทตัวเอง |
| UC-04 | login ไม่สำเร็จ | ทุกคน | กรอกรหัสผิด หรือไม่กรอก | แจ้งเหตุผล ให้กรอกใหม่โดยไม่ต้องพิมพ์ Username ซ้ำ |
| UC-05 | ออกจากระบบ | ทุกคน | login อยู่ | ล้างข้อมูล login กลับหน้า login |

กฎของระบบ
-
| หัวข้อ | กฎ |
|---|---|
| การตรวจรหัสผ่าน | ตรวจกับ TU REST API ทุกครั้ง · ไม่เก็บรหัสผ่านในฐานข้อมูล (`password_hash` = NULL) |
| Application-Key | อ่านจาก environment variable `TU_API_KEY` เท่านั้น ห้าม commit ขึ้น Git |
| ข้อมูลไม่ครบ | ไม่กรอก Username หรือ Password → 400 `VALIDATION_ERROR` |
| รหัสผ่านผิด | → 401 `INVALID_CREDENTIALS` ไม่บันทึกข้อมูลใด ๆ |
| บัญชีถูกปิด | ผู้ใช้ที่ `active = false` → 403 `FORBIDDEN` |
| ระบบ มธ. ขัดข้อง | เชื่อมต่อไม่ได้ / ไม่ได้ตั้ง key → 502 `TU_API_UNAVAILABLE` |
| Role | ผู้ใช้ใหม่: `student` → `STUDENT`, `employee` → `STAFF` · ผู้ใช้เดิมใช้ role ในฐานข้อมูล (`ADVISOR` / `ADMIN` กำหนดในฐานข้อมูลเท่านั้น) |
| อายุ token | 8 ชั่วโมง |
| บัญชีทดลอง | `staff01`, `advisor01`, `6609650001`, `6609650002` ใช้รหัสผ่านทดลองได้โดยไม่เรียก TU REST API · ปิดได้ด้วย `APP_AUTH_DEMO_PASSWORD=` |

Acceptance criteria (test case หลักของ U1 ใช้อ้างอิงใน T11–T20)
-
| เคส | เงื่อนไข |

| TC2 | เจ้าหน้าที่ / อาจารย์ login สำเร็จ แล้วเข้าหน้าตรวจใบสมัครตาม role |

User Story ที่ใช้ U1
-
- U2 ตรวจสอบคุณสมบัติ: นักศึกษาต้อง login ก่อน
- U3 ยื่นคำร้อง / U5 เจ้าหน้าที่: ส่ง `X-User-Id` = `userId` จาก login ไปกับทุก request (`AccessGuard` ตรวจ role)

ไม่อยู่ในขอบเขตของ U1
-
- สมัครบัญชี เปลี่ยนรหัสผ่าน หรือลืมรหัสผ่าน (ทำที่ระบบของมหาวิทยาลัย)
- กำหนด role อาจารย์ / ผู้ดูแลระบบผ่านหน้าเว็บ (กำหนดในฐานข้อมูล)
- ตรวจ token ฝั่ง backend ในทุก API (ตอนนี้ใช้ `X-User-Id` ไปก่อน)
