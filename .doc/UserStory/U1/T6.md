U1:T6 Design Interaction ระหว่าง API_DAO_DB
-
User story U1: นักศึกษาและเจ้าหน้าที่เข้าสู่ระบบด้วย Username และ Password ของสำนักทะเบียน (บัญชี มธ.) เพื่อเข้าใช้งานแอปพลิเคชัน

ระบบไม่เก็บรหัสผ่านเอง แต่ส่งไปตรวจสอบกับ TU REST API ของมหาวิทยาลัย ถ้าผ่าน จึงบันทึกหรืออัปเดตข้อมูลโปรไฟล์ผู้ใช้ลงตาราง `users` แล้วส่ง Token และ Role กลับไปที่หน้าเว็บ

Sequence Diagram
-
![.doc/UserStory/U1/U1-T6 Sequence Diagram.png](<U1-T6 Sequence Diagram.png>)

- **กรณีสำเร็จ** (`status = true`): ค้นหาผู้ใช้ใน DB → สร้างใหม่หรืออัปเดตโปรไฟล์และเวลาเข้าสู่ระบบ → ตอบ `200 OK` พร้อม `LoginResponse`
- **กรณีไม่สำเร็จ** (`status = false`): ตอบ `401 Unauthorized` พร้อม `ErrorResponse` หน้าเว็บแสดงกล่องแจ้งเตือนให้กรอกใหม่
- กรอกข้อมูลไม่ครบ ตอบ `400 Bad Request` · เชื่อมต่อ TU REST API ไม่ได้ ตอบ `502 Bad Gateway`

DAO class diagram
-
![.doc/UserStory/U1/U1-T6 DAO Class Diagram.png](<U1-T6 DAO Class Diagram.png>)

| Method | หน้าที่ |
|---|---|
| `findByUsername(username)` | ค้นหาผู้ใช้จากรหัสนักศึกษา / รหัสบุคลากร |
| `existsByUsername(username)` | ตรวจว่ามีผู้ใช้คนนี้ในระบบแล้วหรือยัง |
| `save(user)` | บันทึกผู้ใช้ใหม่ หรืออัปเดตข้อมูลผู้ใช้เดิม |

ER diagram
-
![.doc/UserStory/U1/U1-T6 ER diagram.png](<U1-T6 ER diagram.png>)

- `username` เป็น Unique Key ใช้ค้นหาผู้ใช้ตอน Log in
- `role` เก็บเป็นข้อความ `STUDENT` / `STAFF` (แปลงจาก `type` ของ TU REST API: `student` / `employee`)
- **ไม่มีคอลัมน์รหัสผ่าน** เพราะตรวจสอบรหัสผ่านกับระบบของมหาวิทยาลัยทุกครั้ง
- ตารางของ User Story อื่น (เช่น คำร้องใน U3) อ้างอิงผู้ใช้ผ่าน `users.id` หรือ `users.username` ได้
